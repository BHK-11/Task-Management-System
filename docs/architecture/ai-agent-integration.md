# TASK OS agent integration audit and architecture

Architecture diagram: [TASK OS agent orchestration](agent-orchestration.html).

**Audit date:** 2026-10-27. Versions and hosted-product behavior below are a point-in-time review of official project pages, not a production security certification. Pin releases and repeat the security review before deployment.

## Existing TASK OS boundary

TASK OS is currently a Java 21 / Spring Boot 4.1.1 application using Spring MVC, Thymeleaf, vanilla JavaScript, PostgreSQL in production and H2 in tests. A private Python FastAPI service proposes a typed plan; it has no TASK OS database connection and executes no application actions. This server-rendered application is not a TypeScript / Next.js app, so this integration does not replace its verified UI or service APIs.

The signed-in Java layer owns the account ID, validates and persists plans, scopes plan reads and decisions to their owner, checks approval again under a database lock, and writes approved personal tasks through `TaskService`. The Python process has a shared service token and provider key; the browser never receives either. The legacy task planner uses a 25-second provider timeout; Phase 15 work planning uses 45 seconds. Both are bounded to 12 steps per plan and 10 plans per account per rolling 24 hours; planner concurrency is capped at four. Submitted instructions and plans are stored in the owner-scoped AI tables; task context is sent only when the user submits it from AI Assist.

The Phase 15 built-in work manager persists `QUEUED`/`RUNNING` state and per-step status in the existing AI plan tables. Its worker leases one plan, processes one task or deliverable at a time, and returns unfinished plans to the queue. Approved task creation uses the canonical `TaskService`; bounded document generation runs in the private Python service. Artifact metadata, size and SHA-256 are stored in PostgreSQL; file bytes are stored outside the static web root and downloaded through an authenticated owner-scoped route. This is not a general external-agent job runner: there is no progress stream, user cancellation, retry control, or external adapter lifecycle. Phase 17 adds partial owner-scoped personal memory and document knowledge. Phase 18 adds a synchronous, read-only Playwright observation worker, but no general browser session or computer-use runtime.

## Master orchestrator and adapter contract

Java remains the only orchestrator. Python may propose plans, and external adapters may return proposals or artifacts, but neither receives database credentials or becomes authoritative for TASK OS identity, tenant permissions, approvals, budgets or execution records.

Every adapter must implement the same versioned contract before it can be enabled:

| Contract field | Requirement |
|---|---|
| Identity and capabilities | Stable `agentId`, pinned adapter/runtime version, and enumerated capabilities; no model-invented provider selection. |
| Input/output | Versioned JSON schemas; request context is minimal and produced by Java. Treat prompts, retrieved content, skill instructions and all adapter output as untrusted. |
| Tools and permissions | Per-run allowlist of typed TASK OS operations; owner/workspace scope is issued by Java and rechecked by Java on every write. Never pass arbitrary user-supplied tool names or IDs through. |
| Execution environment | Explicit sandbox/backend and isolation key. No host filesystem, Docker socket, canonical database, personal browser profile or shared credentials. Egress is denied by default. |
| Limits and approvals | Server-enforced deadline, token/compute/tool-call budgets, maximum output/artifact size, and required human approvals by action class. |
| Lifecycle | Durable job ID and states `QUEUED`, `RUNNING`, `WAITING_APPROVAL`, `SUCCEEDED`, `FAILED`, `CANCELLED`, `EXPIRED`; event sequence, progress stream, cancellation and bounded recovery semantics. |
| Results and errors | Structured proposal, verified artifact references, redacted diagnostic code, and retryability classification. Side effects require idempotency keys and reconciliation before retry. |

The adapter protocol is an implementation seam, not an alternate task service. Java validates the response and applies an approved action through existing owner/workspace-scoped services. Artifacts are stored by TASK OS with tenant ownership and size/type checks; agents return references, never arbitrary filesystem paths.

## Recommended integration sequence

1. Keep the existing TASK OS planner as the only enabled AI capability and expose its real configuration and owner-scoped plan history in Agent Management.
2. Before enabling external agents, add a distinct owner/workspace-scoped agent-job/outbox lifecycle with idempotency, cancellation and recovery. The built-in work queue is scoped to `AiPlan` and does not meet the external-adapter lifecycle contract; do not reuse automation records because the domains have different approval and artifact semantics.
3. When a container runtime is provisioned, add a Hermes worker in a disposable isolated container per job. Give it no direct application DB or host mounts. Allow access only to a private Java tool proxy carrying a short-lived per-job scope; initially deny shell/file/browser tools. Validate cancellation, budgets, egress, duplicate delivery, worker loss and cross-owner access before enabling it.
4. Add Browser Use as a distinct service only for authorized browser-only tasks. Use a fresh profile per run, domain and network egress restrictions, and a user takeover channel for login or sensitive actions.
5. Consider user memory after explicit opt-in, per-account/workspace namespace tests, revocation/deletion, retention policy, secret redaction and permission-aware retrieval are implemented. Keep it separate from Codex’s development memory.
6. Keep third-party skills pinned and reviewed. Scientific skills remain out until a scientific/research task exists; Diagram Design is selected only for documentation diagrams.

## Verification performed and remaining gates

- Audited the local Java/Python services, their current planning/approval records, owner-scoped reads and task execution path.
- Confirmed this host has Python, Java, Node and the Maven wrapper, but no Hermes CLI, Docker or Podman. The repository does not include an isolated agent/browser runtime.
- Reviewed upstream official docs, licenses, release pages and available security policy/advisory pages listed above. This was a source review, not a complete transitive dependency SBOM or penetration test.
- The Phase 15 audit recorded 112 Java tests passing at that point; that historical count is superseded by the Phase 18 regression results below. Coverage includes owner-scoped mixed task/artifact execution and download denial across accounts.
- Ran the installed Diagram Design offline self-check on the architecture HTML successfully.
- A local provider-failure smoke test could not start its loopback HTTP server in this environment. The Java planner was not called against a live provider; the new credential test covers deterministic unconfigured-state handling instead.
- Hermes and an OS/container browser sandbox were **not** run because this host has no Hermes, Docker, or Podman. The Phase 18 Playwright worker was tested in a real Chromium process, but its current local process is not a container/VM security boundary; do not expose it beyond loopback or a separately firewalled worker network.
- Prompt-injection resistance for an external agent, workspace-scoped agent permissions, cancellation/retry, live provider behavior, and production multi-tenant isolation remain unverified. Built-in private artifact storage, owner-only download checks and queue/step execution are covered by local tests, not a production penetration test.
